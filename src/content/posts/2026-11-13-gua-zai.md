docker`镜像`是一层一层叠上来的，`容器`也是在镜像上单独出来一层可写层，只要改动一个文件，即使只改了一个字母，也会把整个文件拉到可写层。大多数linux发行版的文件系统基本都是OverlayFS / overlay2，如alpine,debian，用`docker commit`将容器打包为新镜像时，那个副本就会完整地写入镜像的顶层，像`数据库`这类`体积庞大`，而且要`持久存储`，不能随容器删除而删除的，一旦改动再用commit构建镜像，新旧两份都会在历史层。

当然上面那个数据库的例子主要还是要持久存储这个原因，毕竟一般不会用docker commit去构建镜像。

那么这里就要用到`挂载`了。docker的挂载就是类似linux系统的挂载功能，`linux的挂载`是把物理存储的卷或其他设备，挂载到文件系统的目标目录。而`docker的挂载`是把宿主机的目录挂载到容器里的目录。

用挂载的其中一个好处就是镜像更新了，直接用新的镜像运行，挂载上需要的数据就能无缝切换，不用考虑数据被更新覆盖的问题。

docker的挂载分为三种：`volume `/ `bind mount` / `tmpfs`
- `volume`：由docker管理，默认放在`/var/lib/docker/volumes`。官方不推荐手动修改宿主机真实位置的文件。

  创建volume：
  ```bash
  docker volume create [my_volume]
  ```

  查看volume信息
  ```bash
  docker volume inspect [my_volume]
  ```
  输出类似
  ```bash
	[
	    {
	        "CreatedAt": "2026-11-13T09:37:20+08:00",
	        "Driver": "local",
	        "Labels": null,
	        "Mountpoint": "/var/lib/docker/volumes/demo/_data",
	        "Name": "demo",
	        "Options": null,
	        "Scope": "local"
	    }
	]
	```
  挂载示例：
  ```
  ```bash
  docker run -d -v [my_volume]:/app/data [my_image]
  ```
  - 其中volume不是必填的，如果不填，就会是匿名卷。\
  匿名卷在容器被删除后仍然保留,但如果创建容器时用了 `--rm`,这个容器关联的匿名卷会随容器一起销毁(D05-13)。命名卷则完全不受 `--rm` 影响。
  ```bash
  小实验
  docker volume ls -q | wc -l
  docker run --rm -v /anon alpine true
  docker volume ls -q | wc -l
  docker run --rm -v keepvol:/keep alpine true
  docker volume ls -q | grep -c keepvol
  ```
  可以看到，第二次 wc -l 与第一次相同(匿名卷被 --rm 一起清掉了);最后 grep -c 输出 1
- `bind mount`
这就是常见的直接把宿主机目录直接挂载到容器，和volume的主要区别是在宿主机可以自定义位置，并且修改。
  挂载示例:
  ```bash
  docker run -d -v [my_volume]:/app/data [my_image]
  ```
- 挂载有两种写法:短的 `-v(--volume)`和长的 `--mount`。它们不是同义词——官方一般推荐 --mount,因为它更显式、支持全部可用选项。`-v` 把三个字段用冒号排在一起([卷名:]容器内路径[:选项]),第三段对数据卷只支持 ro、volume-nocopy 等少数选项。而 `--mount` 用 key=value 写,还额外支持 volume-subpath、volume-opt、volume-driver、bind-create-src。

  -v/--mount对比示例：
  ```bash
  # 把demo这个volume挂载到容器内的目录
  -v:
  docker run -v demo:/x alpine ls -ld /x
  --mount:
  docker run --mount type=volume,src=demo,dst=/x alpine ls -ld /x
- `tmpfs`只活在主机内存里,容器一停就没了;因为它用的是内存,用量会计入容器的 memory cgroup 限额。\
它还`不能`在容器间`共享`,而且底层是内核 tmpfs,数据可能被换进 swap。

- 如果要挂载的目录不为空，会怎么样呢？bindmount/tmpfs和liux的挂载差不多，无论如何，挂载目录也就是容器内里原有内容会被`隐藏`，取消挂载就会`恢复`隐藏。\
  volumn有点不一样，当一个`全新的空卷`被挂载到有内容的容器目录时，那个目录里的内容会被复制一份到卷里，然后隐藏。如果`卷不为空`，那就像bind mount一样直接隐藏挂载目录内容。

# volume备份
卷在 /var/lib/docker/volumes/ 下,官方明确不要直接去动它。那怎么备份?官方套路是用一个临时容器把卷挂进来,再用 tar 打包到宿主的一个目录。
先看一条命令，比如要备份my_container容器的/dbdata目录
```bash
docker run --rm --volumes-from [my_container] -v $(pwd):/backup alpine tar cvf /backup/backup.tar /dbdata
```
`--volume-from`:\
查找名为 my_container 的容器，并读取它的所有卷挂载配置，然后将完全相同的挂载配置应用到新容器上。
这条命令做的就是新建一个容器，把要备份的容器的volume全挂载到自己身上，这样就可以打包了。\
看懂了之后就有新问题了，明明可以exec进容器，一句tar命令解决的事情，为什么要搞这么复杂？
1. 工具与业务镜像解耦
你不需要保证业务镜像里存在 tar。很多生产镜像为了精简和安全，根本不包含打包工具。临时容器可以选用任何带有 tar 的镜像（如 alpine），完全不受业务容器限制。

2. 写入隔离与安全护栏
临时容器可以以 只读（:ro） 方式挂载源卷，从挂载层面杜绝备份过程意外修改原始数据。如果用 docker exec 进入业务容器，你继承的是它的读写权限，没有这层保护。

3. 结果落盘的清晰路径
官方示例会同时挂载宿主机目录作为输出端（如 -v $(pwd):/backup），让生成的 tar 文件直接落在宿主机上，而不是先写进被备份的卷里、再想办法拷出来。官方指南还特别提醒：不要把 tar 写回正在备份的同一个卷，否则归档文件会把自己也打包进去，导致体积异常膨胀。

4. 用完即删，零残留
官方模式使用 --rm 标志，辅助容器退出后立即被移除，不会在宿主机上留下任何多余的容器状态。
